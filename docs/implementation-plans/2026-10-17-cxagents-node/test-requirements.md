# Test Requirements: cxagents-node

## Overview

This is a homelab dotfiles repo of shell scripts, justfiles, compose files, a HuJSON tailnet policy and (new in this plan) one small Go module. There is **no test framework at the repo level**. As in `docs/implementation-plans/2026-10-11-connectome-agent/test-requirements.md`, "tests" here are operational, plus Go unit tests confined to the forwarder module. Each acceptance criterion (AC) is proven by one or more of the following.

- **Go unit tests (`unit`).** These use Go's `testing` package inside `stacks/cxagents/forwarder/` (module `tailnet-forwarder`) only. Go is not installed on the host, so tests run in the digest-pinned `golang:1.27.1-bookworm` builder through `stacks/cxagents/scripts/go.sh` (`dotfiles stacks cxagents test` = `go.sh test -count=1 ./...`). They also run in the Dockerfile's `test` stage (`go vet ./... && go test -count=1 ./...`), so a regression fails `dotfiles stacks cxagents build` and leaves `build.lock` unchanged.
- **One TypeScript unit test outside the repo (`unit`).** This is `test/web-ui-module.test.ts` in the `~/Developer/connectome/connectome-host` clone (branch `local`). It runs with `bun test` in an `oven/bun:1-debian` container on `colima-agents`, against a read-only copy of the clone.
- **Bash check scripts (`script`).** They print one `pass`/`fail` line per check (`stacks/scripts/lib/check.sh`) and exit 1 on any FAIL:
  - `tailscale/scripts/smoke.sh`: live checks against the tailnet that never change the live policy (`dotfiles tailscale smoke`), with functions `check_acN_M`.
  - `tailscale/scripts/lint.sh` + `tailscale/scripts/lint-test.sh`: policy invariants 0–3 and their single-violation fixtures (`dotfiles tailscale lint|lint-test`).
  - `tailscale/scripts/doctor-test.sh`: fixture runner for every FAIL/WARN path of `tailscale/scripts/doctor.sh` (`dotfiles tailscale doctor-test`).
  - `tailscale/scripts/keyscan.sh --repo|--names [--no-pat]`: owns the forbidden credential key names.
  - `stacks/cxagents/scripts/image-test.sh`: checks 1–6 against `tailnet-forwarder:local`.
  - `stacks/cxagents/scripts/lint.sh` + `lint-test.sh`: cxagents invariants 1–7 and their fixtures.
  - `stacks/cxagents/scripts/login-test.sh`: the state/device matrix, cases 1, 2, 2b, 3, 4, 5, 6.
  - `stacks/cxagents/scripts/smoke.sh`: Phase 5 identity/isolation checks plus Phase 6 end-to-end checks run from the Mac over the tailnet. It has a `--long` flag.
  - `stacks/cxagents/scripts/doctor-test.sh`: fixture runner for every FAIL path of `stacks/cxagents/scripts/doctor.sh`.
  - `stacks/cxagents/scripts/build.sh`: refuses unpinned inputs and writes `build.lock`.
  - Connectome's existing `lint.sh`, `lint-test.sh`, `image-test.sh` and `smoke.sh`, which are re-run as regression.
- **`dotfiles stacks doctor` (`doctor`).** `stacks/scripts/doctor.sh` gains two sections. Each re-emits the `[OK]/[FAIL]/[WARN]/[OFF]` lines of a module-local script, so credential key names stay inside `tailscale/` (AC2.5):
  - `--- Tailnet ---` from `tailscale/scripts/doctor.sh` (checks 1–8: credentials file, policy drift, clients, identity, Tailnet Lock, policy lint, retired PAT, keyscan);
  - `--- cxagents ---` from `stacks/cxagents/scripts/doctor.sh` (checks 1–7: VM, image, state, container health, node `check`, routes targets, cxagents lint).

  Doctor is the ongoing regression suite after the plan completes.
- **Operational commands with an exact expected output (`operational`).** These are written in a task's Verify step. Examples: `TAILSCALE_ENV_FILE=/nonexistent ./stacks/adguard/scripts/tailnet-dns.sh on; echo "rc=$?"` and `diff` of two `build.lock` files.

A second class of AC parts needs a human, and only the operator can do them:

- approve live writes (the policy pushes, the `.env` key rename, the first device registration);
- create the `dotfiles-authkeys` OAuth client and type its secret;
- check connectivity from cxmacbook and cxphone;
- check the browser certificate;
- restart the agents VM;
- run the 10-minute WebSocket idle test (`smoke --long`);
- run a full `down-all`/`up-all`;
- rebuild on a fresh device or a new tailnet;
- change the password-manager setting;
- do the PAT cutover after the merge;
- review documentation content.

These gates are listed per AC below and consolidated at the end. **Mixed** ACs need both an automated check and a human gate.

### Verification-type categories

| Category | Meaning in this plan |
|---|---|
| Automated (unit) | A Go `go test` in the pinned builder (also run in the image build), or the connectome-host `bun test`. |
| Automated (script) | A dedicated check script (`smoke.sh`, `lint-test.sh`, `doctor-test.sh`, `login-test.sh`, `image-test.sh`, `build.sh`), with the named check/fixture/case. |
| Automated (doctor) | The primary proof is a `dotfiles stacks doctor` check, which keeps asserting it on every later run. Its FAIL/WARN paths are proven by a `doctor-test.sh` fixture. |
| Automated (operational) | A one-off verification command in a task step with an exact expected output. A human may have to *approve* running it; the pass/fail judgment itself is mechanical. |
| Mixed | An automated check covers part of the AC. A human action or observation is required for the rest. |
| Human | Only a person can judge pass/fail. Supporting automated evidence is noted. |

### Phase file numbering

`phase_0N.md` = design Phase N (1–7). This differs from the connectome-agent plan, where numbering was offset by one. Citations below are `phase_0N Task M` (with Step/check/case where useful). All files are in `docs/implementation-plans/2026-10-17-cxagents-node/`. Convention used by every phase: `J="just -f $wt/justfile"`. The `dotfiles` alias is never used while executing, because it points at `main`.

### Implementation decisions this mapping relies on

These planning-time decisions change *how* a design AC is verified. They explain mappings that would otherwise look inconsistent with an AC's literal wording.

1. **Member→member swap happens in Phase 1, not Phase 3** (phase_01 Decision 1). The pulled live policy has a `*`→`*` grant, which the Phase 1 lint (invariant 1) forbids, so Phase 1 already replaces it with `autogroup:member`→`autogroup:member`.
   - **AC5.1:** the connectivity confirmation is first needed after the Phase 1 push (phase_01 Task 7 Step 4) and again after the Phase 3 push (phase_03 Task 1 Step 5).
   - **AC1.7, member half:** `check_ac1_5_validate` proves that validate rejects a policy *without* the member→member grant.
2. **Git-lineage rule for plain `policy-push`** (phase_01 Decision 2). Plain push refuses unless the *live* policy is byte-identical to some committed version of `policy.hujson` in git history. That one rule covers both "new tailnet" (live is Tailscale's default, never committed) and "admin-console edit" (drift).
   - **AC1.8:** "refuses there" is proven by `check_ac1_8_refuse` with a temp git repo whose only commit is *not* the live policy.
   - The rule implies "commit `policy.hujson` right after every successful push". `policy.sh push` prints that reminder, and AC1.3's follow-up commit (phase_01 Task 7 Step 6) depends on it.
3. **Test seams instead of live mutation** (phase_01 Decision 3; phase_02/03/05/07 analogues):
   - `TAILSCALE_ENV_FILE`, and `policy.sh`/`lint.sh --file F` (lineage uses F's own git repo).
   - `TS_POLICY_TEST_STALE_ETAG=1`: AC1.4's 412 path uses an all-zero `If-Match` rather than a real concurrent admin-console edit.
   - The doctor-test overrides (`TAILSCALE_POLICY_FILE`, `TAILSCALE_CLIENTS_CONF`, `TAILSCALE_TAILNET_CONF`, `TAILSCALE_STATUS_JSON`, `TAILSCALE_LOCK_STATUS`, `DOCTOR_ENV_FILES`).
   - The login seams (`CXAGENTS_IMAGE`, `CXAGENTS_STATE_VOLUME`, `CXAGENTS_DEVICES_JSON`, `CXAGENTS_AUTHKEY_CMD`, `CXAGENTS_LOGIN_DRY_RUN`).
   - The cxagents doctor seams (`DOCTOR_CXAGENTS_CONTAINER`, `DOCTOR_CXAGENTS_ROUTES`, `DOCTOR_CXAGENTS_CHECK_CMD`).

   The smoke never changes the live policy: every push it attempts is declined, stopped by lint/validate, or sent with a stale `If-Match`. Each live-touching check ends by asserting that the live ETag is unchanged.
4. **AC2.5 is narrowed, and `keyscan.sh` owns the key names** (phase_01 Decision 4 and the "Credential key names stay inside `tailscale/`" convention).
   - `keyscan.sh --repo` scans tracked files *excluding* `tailscale/`, `archive/` (frozen) and the planning docs `docs/{design,implementation,test}-plans/`, which necessarily name the keys. Operational docs such as `docs/migration-recovery.md` stay scanned.
   - Code that must name a key builds it from fragments: the Go `os.Unsetenv` list in `internal/node`, and the fixture names in `stacks/cxagents/scripts/lint-test.sh`.
   - `TAILSCALE_PAT` joins the list in Phase 2. `keyscan.sh --names --no-pat` (phase_05 Task 2) drops it again for the cxagents lint, so a leftover PAT line in the live adguard `.env` before the post-merge cutover counts as doctor's AC4.7 WARN, not as a lockdown FAIL.
5. **The validate failure shape is probed before it is relied on** (phase_01 Task 6 Step 1). `policy.sh push` treats a non-2xx response *or* a 200 with a non-empty `.message` as a validate failure. If the probe returns 200 with an empty `.message` (validate doesn't run tests), the executor STOPs. AC1.5 (validate half) and AC1.7 depend on this.
6. **The live system keeps the PAT until the merge** (phase_02 "The live system keeps using the PAT"). Inside the worktree, `stacks/adguard/.env` is replaced by a secret-free 0600 file (phase_02 Task 1), so AC3.1/AC3.3 are proven there with no `TAILSCALE_PAT` in any worktree file. The live `stacks/adguard/.env` is cleaned and the PAT revoked only in the post-merge cutover (`tailscale/README.md` "PAT revocation"; phase_07 Task 8 Step 2 item 4). Until then, doctor run from `main` is *expected* to show the AC4.7 `TAILSCALE_PAT` WARN.
7. **Doctor checks live in module scripts.** `tailscale/scripts/doctor.sh` (phase_02 Task 4) and `stacks/cxagents/scripts/doctor.sh` (phase_07 Task 1) are re-emitted by `stacks/scripts/doctor.sh` (phase_02 Task 5; phase_07 Task 2), and each has a fixture runner (`doctor-test.sh`). The fixtures run against the real tailnet/VM read-only:
   - **AC4.2's "admin-console edit"** is simulated by a repo-side copy with `// drift` appended (repo bytes ≠ live ETag looks identical to doctor).
   - **AC4.5's "forwarder stopped"** is simulated by pointing at a non-existent container name. A live stop is operator-optional (phase_07 Task 3 Step 3).
8. **The AC2.6 tags check depends on the phase_03 Task 3 probe outcome:**
   - **(a)** If the token-exchange response carries the client's tags, doctor compares them exactly with `clients.conf`.
   - **(b)** If tags aren't visible but are enforced at exchange, doctor checks that an exchange requesting exactly the declared tags succeeds *and* one requesting `tag:doctor-undeclared-probe` fails. In this branch, extra tags on the client are unobservable with these scopes, and the user must agree that this satisfies AC2.6 *before* it is implemented.
   - **(c)** If tags are neither visible nor enforced, the executor STOPs and asks.

   The `tags-mismatch` fixture (authkeys row declaring `tag:other`) FAILs under both (a) and (b).
9. **AC2.4 cannot write by accident.** The authkeys-client ACL POST carries an all-zero `If-Match`, so even a wrongly accepted call gets 412 and writes nothing; a 412 is a FAIL (the scope was accepted). The DNS POST re-sends the current nameserver list.
10. **"Accept, then dial"** (phase_04 Decision, operator 2026-10-17; a deviation from the design's Forwarder contract step 4). The tsnet fallback callback holds tsnet's main mutex, so it does only in-memory checks: route, deny list, subnet check against a pre-resolved target cache, in-flight caps. Any failure → `(nil, true)` = RST. The **handler goroutine** dials with a 2 s timeout. Consequences for verification:
    - **AC6.5 and AC6.7:** with nothing listening (or only on `127.0.0.1`), the client sees "connected, then closed/reset" (linger-0 RST where supported, otherwise FIN), **not** "connection refused". The tests assert failure within the time bound (`handler_test.go` within 2 s; `check_ac6_5` ≤ 3 s) and immediate success once a server starts. They do not assert ECONNREFUSED.
    - **AC6.6:** ports 3100 and < 1024 are dropped by the tailnet packet filter *before* the callback (policy-denied SYNs never reach it), so the client times out. `check_ac6_6` uses `nc -z -w 3` failure, not "refused". `decide_test.go` separately proves a denied port that does reach the callback is RST.
    - **AC6.11:** "never dialed" holds by construction (the callback never dials). `decide_test.go` proves an off-subnet target gets `(nil, true)` and triggers `Refresh`.
11. **Phase 5/6 stacks run from the worktree until the merge.** After the merge, `cxagents up` and `connectome up` must be re-run from `main` (phase_07 Task 8 Step 2 items 2–3). A pre-merge reboot runs `main`'s `up-all`, which knows nothing of cxagents, so re-run from the worktree. This does not change any mapping, but the human checklist must include it.
12. **The WebUI guard patch lives outside the repo,** in the `connectome-host` clone (`local` branch). It is unit-tested with `bun test` in a container (phase_06 Task 3) without touching the clone's working tree, so `connectome build`'s clean-tree check still passes. It is recorded in `stacks/connectome/sources.lock` by `connectome build`, and asserted by connectome `image-test.sh` check 13 (phase_06 Task 4).
