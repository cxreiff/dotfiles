# Test Requirements: stack-resilience

## Overview

This is a homelab dotfiles repo of shell scripts and YAML; there is no test framework (jest, pytest, etc.). Per the design plan's "No explicit test framework" note, "tests" are operational: each phase's verification is the act of running a recipe and observing its effect, with `dotfiles stacks doctor` acting as the ongoing assertion suite. Doctor accumulates checks across phases (infrastructure, host volumes, backup age, DNS failover, IP coupling, .env key presence, homebridge identity) and is treated as the single read-only diagnostic that proves the system is in its expected state. Most ACs map to either a doctor check, a phase-local verification command (e.g. `tar tzf <tarball> | head`, `launchctl print gui/$UID/com.cxreiff.dotfiles.backup`, `./scripts/gen-pin.sh` in a 100-iteration loop), or a paired script + recipe invocation.

A second class of ACs needs a human in the loop: anything that requires logging into a web UI (freshrss, wallabag, homebridge, AGH first-run wizard), checking pairing state in the iOS Home app, configuring the RT-AC68U router (WAN DNS and DHCP DNS advertisement), generating a Tailscale PAT and pasting it into `.env`, or visually confirming the bridged-ip-changed checklist. These manual gates are called out explicitly per phase and consolidated at the bottom of this document. Mixed ACs require both classes (e.g. AC1.3 — the migration script writes data, but only a human browser session can confirm that the `cxreiff` user can log in to freshrss with pre-migration feeds intact).
