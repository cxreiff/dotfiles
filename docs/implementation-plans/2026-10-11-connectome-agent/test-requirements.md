# Test Requirements: connectome-agent

## Overview

This is a homelab dotfiles repo of shell scripts, justfiles, compose files and JSON recipes. There is no test framework at the repo level. As in `docs/implementation-plans/2026-05-03-stack-resilience/test-requirements.md`, "tests" here are operational. Each acceptance criterion (AC) is proven by one or more of:

- **A dedicated test script** with one `pass`/`fail` line per check, exit 1 on any FAIL:
  - `stacks/connectome/scripts/image-test.sh` (static assertions against the built images, rows 1–13; `dotfiles stacks connectome image-test`);
  - `stacks/connectome/scripts/smoke.sh` (assertions against the running stack, checks 1–15, restores what it changes; `dotfiles stacks connectome smoke`);
  - `stacks/connectome/scripts/lint-test.sh` (generated single-violation fixtures for `lint.sh`; `dotfiles stacks connectome lint-test`);
  - `stacks/onecli/scripts/probe.sh` (gateway identity/policy probes from a throwaway curl container on `onecli-agents`; `dotfiles stacks onecli probe`);
  - `stacks/connectome/scripts/ratelimit-check.sh` (rule-1 hard ceiling; `dotfiles stacks connectome ratelimit-check`);
  - `stacks/connectome/scripts/force-failure.sh` (forced inference failure; `dotfiles stacks connectome force-failure`).
- **Unit tests in the local clones.** They use the clone's own runner (`node --import tsx --test`, node:test + assert/strict) and also run inside the image build, so a regression fails `dotfiles stacks connectome build`:
  - `~/Developer/connectome/heartbeat-mcpl/test/reminder-floor.test.ts`;
  - `~/Developer/connectome/discord-mcpl/test/attachment-root.test.ts` (Linux-only, so it runs in a `node:22-bookworm` container on `colima-agents`).
- **`dotfiles stacks doctor`** (`stacks/scripts/doctor.sh`). It gains a new `--- Agents (onecli + connectome) ---` section, connectome entries in `--- Stack volumes ---` and `--- Backups ---`, a `.env` mode-0600 check in `--- Stack identity & env ---`, and the static invariant lints (`stacks/connectome/scripts/lint.sh`). It is the ongoing regression suite after the plan completes.
- **Operational commands with an exact expected output**, as written in a task's Verification/Testing step (e.g. `docker … image ls | grep … || echo "OK: image gone"`, `just -f stacks/justfile --show down-all`).

A second class of ACs needs a human in the loop. Only the operator can do these:

- send Discord DMs from the operator account and from a second account;
- observe a reply, or an attachment arriving, in the Discord client;
- watch WebUI live (WebSocket) updates and the quota meter in a browser;
- complete the ChatGPT device-code login (`codex login --device-auth`);
- set the ChatGPT per-app weekly cap in ChatGPT settings;
- enter the onecli operator email/password;
- run `sudo` steps (`launchctl`, plist removal, `fdesetup authrestart`);
- confirm destructive steps (v1 volume removal, connectome restore rehearsal);
- judge documentation content.

These gates are listed per AC below and consolidated at the end. **Mixed** ACs need both an automated check and a human gate.

### Verification-type categories

| Category | Meaning in this plan |
|---|---|
| Automated (doctor) | The primary proof is a `doctor` check, which keeps asserting it on every later `doctor` run (including fixture-driven FAIL/WARN proofs of doctor itself). |
| Automated (recipe) | A `dotfiles …` recipe or a one-off operational command run by the executor, with an exact expected output written in the task. |
| Automated (script) | A dedicated test script (`image-test.sh`, `smoke.sh`, `lint-test.sh`, `probe.sh`, `ratelimit-check.sh`), a clone unit test, or a script-under-test exercised against temp fixtures (`init-env.sh`, `build.sh`, `backup-rotate.sh`). |
| Mixed (automated + human) | An automated check covers part of the AC; a human action or observation is required for the rest. |
| Human | The pass/fail judgment can only be made by a person. Supporting automated evidence is noted. |

### Phase file numbering

`phase_0N.md` = design Phase N−1. Citations below are `phase_0N Task M` (Step/row/check where useful). All files are in `docs/implementation-plans/2026-10-11-connectome-agent/`.

### Implementation decisions this mapping relies on

These are the planning-time decisions that change *how* a design AC is verified. They explain several mappings that would otherwise look inconsistent with the AC's literal wording:

1. **"Gateway log shows the request" means the Postgres `request_logs` table** (AC6.2, AC6.4, AC7.2, AC10.1, AC10.2, AC3.7 measurement). onecli 2.12.0 doesn't print allowed requests on gateway stdout. They are read with `dotfiles stacks onecli requests <minutes>` (phase_02 Task 4; columns time, agent_id, method, host, path, status). The host agent id comes from `source stacks/onecli/scripts/lib/api.sh; agent_field connectome-host id`. Gateway stdout only carries refusals (`BLOCKED by policy rule`, `RATE LIMITED`, `egress guard: refused`).
2. **"No `blocked_by_policy` in the gateway log" (AC6.3) is a grep for the stdout refusal lines**, since the JSON code `blocked_by_policy` is returned to the client, not logged: `docker logs onecli-gateway --since <start> | grep -cE 'BLOCKED|RATE LIMITED|refused'` → `0`, cross-checked against `onecli requests 5` (no 403s).
3. **Spike-observed gateway statuses are the arbiter** (AC3.4–AC3.6): 407 with no token, 401 `access_restricted` for the shell on chatgpt.com, 403 `blocked_by_policy` for blocked paths. `probe.sh` asserts these. If a status differs, the executor stops and reports; it does not edit the expectation (phase_02 Task 8 Step 3).
4. **AC5.4 is forced by stopping the gateway, not by swapping the model** (swapping models on a live chronicle breaks continuity). `force-failure.sh` stops `onecli-gateway`, waits up to 180 s for the operator's DM to produce a new `failures.log` record, and always restarts the gateway via `trap` (phase_03 Task 12).
5. **The live heartbeat wake gate is changed with `set-heartbeat-rate.sh`** (AC10.2, AC3.7). agent-framework seeds `$DATA_DIR/sessions/<id>/config/gate.json` from the recipe once, so editing `recipes/agent.json` does not affect an existing session (phase_03 Task 14). The recipe is kept in sync by hand for new sessions.
6. **AC10.3 resets the gateway's in-memory rate counter by restarting `onecli-gateway`** after temporarily setting rule 1 to 2/hour. The PATCH alone does not reset the counter (keyed by rule × token × clock hour). The test expects HTTP 429 on the 3rd POST plus a `RATE LIMITED` stdout line, and restores the remembered limit via `trap` (phase_03 Task 14 Step 3).
7. **AC12.2 uses fixtures generated on the fly** from the tracked files: recipe, `compose config --no-interpolate --format json`, `.env.example` key lines, Dockerfile. Each mutation must produce `[FAIL] invariant N` for exactly its N and no other FAIL. A negative fixture for AC12.5 puts the invariant key names only in a *value* and expects zero FAILs (phase_04 Task 5).
8. **The AC12.3 CA-mismatch proof uses a throwaway fixture image** selected through `DOCTOR_CONNECTOME_IMAGES`. **AC12.4 uses `DOCTOR_LLM_CALLS_WARN_MB=0`/`DOCTOR_HEADLESS_LOG_WARN_MB=0`** rather than growing real logs (phase_04 Task 6).
9. **AC11.1's failure path is induced harmlessly** with `chmod 000 stacks/freshrss/compose.yaml`, so compose can't load the file and no container is touched (phase_04 Task 1). **AC11.5 truncation is proven on a fixture volume** (`cx-trunc-test`, 51 MiB log), not the live log (phase_04 Task 3).
10. **The nightly backup daemon is paused** from phase_02 Task 1 Step 0 until phase_04 Task 8 Step 0. Any doctor backup-age PASS before then (phase_02 Task 9, phase_04 Task 6) depends on manual backups: worktree recipes for onecli/connectome, main's justfile for the unchanged stacks. **AC11.8 (reboot) can only run after the local merge** in phase_04 Task 8 Step 0, because the startup daemon runs main's recipes.
