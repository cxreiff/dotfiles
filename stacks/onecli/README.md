# onecli stack

[onecli](https://github.com/onecli/onecli) v2 — credential vault that gives AI
agents access to services without exposing keys. Runs in the `agents`
Colima VM as the credential broker for [connectome](../connectome/).

Four services in one Compose project: migrations (setup, one-off), a
Postgres 18 instance for the encrypted ciphertext store, a Next.js dashboard,
and a Rust gateway (`localhost:10255` — the proxy identity broker). All
images pinned to v2.12.0, all arm64.

**Two pieces of asymmetry vs the other stacks:**

- State lives in Docker named volumes inside the `agents` VM, not
  under `~/.volumes/onecli/`. See [Volumes](#volumes).
- Secrets are generated by `init-env` and guarded by `:?` in compose.
  The vault has no default identity; agents select their identity via
  the proxy token. See [Auth (v2)](#auth-v2).

## Fresh-device setup

Prerequisites: Stage 2 setup complete (`dotfiles stow setup-colima`
already run), plus the host `onecli` CLI on PATH. If you don't have it:
`curl -fsSL onecli.sh/cli/install | sh`. The `agents` VM is on-demand;
bring it up first.

```sh
dotfiles stacks vm-agents-up

cp .env.example .env
chmod 600 .env
dotfiles stacks onecli init-env               # generates three secrets; escrow in password manager

dotfiles stacks onecli up                     # first boot — Docker creates onecli_pgdata + onecli_app-data
dotfiles stacks onecli ps                     # api, web, gateway healthy; migrations exited 0
dotfiles stacks onecli bootstrap              # required: register account, create operator identity
dotfiles stacks onecli import-openai          # required (fresh vault only): dedicated device login for ChatGPT
dotfiles stacks onecli policy                 # required: define connectome agent and allow rules
```

`init-env` is idempotent and never prints secret values. After it runs, set
an escrow copy of `SECRET_ENCRYPTION_KEY` in the password manager (used on
fresh-device recovery). After `bootstrap`, the dashboard is at
`http://127.0.0.1:10254` + the host `onecli` CLI works from any shell on the
Mac. The gateway is unreachable except via proxy auth (`aoc_` tokens).

## .env keys

| Key | Purpose |
|---|---|
| `SECRET_ENCRYPTION_KEY` | AES-256 key for vault ciphertext (generated by `init-env`, **backup to password manager**) |
| `BETTER_AUTH_SECRET` | BetterAuth session seed (generated by `init-env`) |
| `GATEWAY_INTERNAL_SECRET` | Gateway-to-api authentication (generated by `init-env`) |
| `POSTGRES_USER` | Postgres role. Default `onecli` is fine |
| `POSTGRES_PASSWORD` | Postgres password (generated by `init-env`; `:?` guard prevents start without it) |
| `POSTGRES_DB` | Database name. Default `onecli` is fine |
| `ONECLI_BIND_HOST` | (optional) Dashboard bind. Defaults to `127.0.0.1` |
| `ONECLI_APP_PORT` | (optional) Dashboard port. Default `10254` |
| `ONECLI_GATEWAY_PORT` | (optional) Gateway port. Default `10255` |

`.env` is gitignored and kept at mode 0600; `.env.example` is the tracked template.
Never add an onecli **user** API key to `.env` — the vault is for service/LLM credentials,
not the operator's vault login. The operator (on the Mac) logs in via the dashboard.

## Auth (v2)

onecli v2 requires account login:

1. **Dashboard:** `http://127.0.0.1:10254` on the Mac (over Colima's `network.mode: shared` port forward).
   Registration is open on first `up`; register immediately.
2. **Host CLI (`onecli` binary):** login with your account credentials. Run `onecli secrets list` and other operations.
   The `.onecli/config.json` points to `http://127.0.0.1:10254`; the CLI caches an API key (`~/.onecli/credentials/`).
3. **Proxy identity (agents):** agents select their identity via the `HTTPS_PROXY` `aoc_` token. No default identity exists.
   A CONNECT without a valid token gets a 407 error. Each agent (connectome-host, connectome-shell, future personas)
   holds a distinct token.

## Key location and FileVault

The `SECRET_ENCRYPTION_KEY` lives in `stacks/onecli/.env` (0600, gitignored, with
an escrow copy in the password manager). Tarballs hold ciphertext + gateway CA only,
never the key itself. FileVault protects the live `.env` on disk and the agents VM
disk image at rest. On fresh-device recovery:

1. Restore `onecli` tarball to empty volumes.
2. Create `.env` with the escrowed `SECRET_ENCRYPTION_KEY` (and other secrets from the password manager).
3. `dotfiles stacks onecli up` — the vault unlocks with the key.

## Identities and policy

onecli grants credentials to agents via explicit policy rules. Each agent holds a distinct
`aoc_` token (the proxy credentials) that identifies it when requesting injected secrets.

**Identities:**

- `connectome-host` — the connectome agent host (Bun/TypeScript). Injects the `openai` OAuth secret (ChatGPT subscription tokens).
- `connectome-shell` — the connectome agent's shell (Linux workbench). No LLM grant; reaches services via `connectome-host`'s proxy.

**Policy rules** (`dotfiles stacks onecli policy`):

- `rule 1`: rate limit (1000 requests/hour per agent). Operators on the personal plan may consume their full quota; no per-app ChatGPT cap.
  Run `dotfiles stacks connectome ratelimit-check` to see current usage and remaining tokens.
- Injection scope: agents select their identity via the `aoc_` token; injection applies to the host-IP (`chatgpt.com`, `api.openai.com`, etc.)
  and method, not per-path.

**Path rules** (onecli design):

- `Network` rules filter by `pathPattern` (prefix-glob). Path rules are **defense-in-depth only**: a dot-segment bypass (`../../..`)
  can escape the pattern. Report such bypass in the upstream issue. Intended usage: allow data-reads but block token refreshes.
- Private-destination refusal covers proxied requests only (loopback, RFC1918, Tailscale). Unproxied direct connections are not filtered.

Run `dotfiles stacks onecli policy` to review and edit rules; `dotfiles stacks connectome probe` to test the proxy.

## Threat model

**What we defend against:**

- Credentials leak from connectome container memory, logs, or disk: the vault keeps them server-side. Agents see only tokens
  (`aoc_` for proxy, `onecli-managed` Codex stub), never the real secrets. The gateway's TLS MITM injects the real token on `chatgpt.com`.
- Credential loss if a connectome container is compromised: the gateway is unreachable from inside the VM without the `aoc_` token.
  There is no `host.docker.internal` or published port; the gateway only listens on VM-loopback and rejects requests without a valid
  agent identity.

**What we accept:**

- Same-UID compromise on the Mac: an attacker running code as your UID can `curl http://127.0.0.1:10254` (the dashboard) and read every
  credential plaintext, or proxy through the gateway with a stolen `aoc_` token. There is no auth in front of the gateway inside the VM.
  Same-UID compromise = vault compromise.
- Connectome's direct egress: the shell can reach the LAN and Tailscale directly (not through the gateway). Intended for agent tooling.
  Locking this down is future work (see design Phase 3's Known exposures).

**Backup tarballs:** are ciphertext + gateway CA only (no key, no plaintext secrets). They are stored under `~/.volume-backups/`
and protected by FileVault.

## Volumes

| Volume (Docker named, project-prefixed) | Container path | Contents |
|---|---|---|
| `onecli_pgdata` | `/var/lib/postgresql` | AES-256-GCM ciphertext of stored credentials |
| `onecli_app-data` | `/app/data` | Gateway CA certificate and key (CA, not the vault key) |

### Why named volumes (and not `~/.volumes/onecli/`)

Every other stack in this repo uses bind mounts under `~/.volumes/<stack>/`. onecli does not.

What's at stake: `pgdata` holds the AES-256-GCM ciphertext of all credentials. Inside the VM, the vault key is loaded from
`.env` into the gateway's memory at startup. Keeping the ciphertext inside the VM rather than on the Mac filesystem removes a
class of accidental disclosure paths:

- backups of `~` that don't know to exclude `~/.volumes/`
- screen shares, `find ~`, `ls -laR ~`, anything that walks the home tree
- malware or grep-based scrapers looking for files matching common DB extensions

The cost of breaking repo symmetry here is one custom backup recipe and a small special-case in `doctor.sh`; the benefit is
removing unintended data leaks.

## Backup notes

`dotfiles stacks onecli backup` runs `compose stop`, snapshots the named volumes via a throwaway `alpine` container, and runs
`compose start`. The tarball lands at `~/.volume-backups/daily/onecli-YYYY-MM-DD.tgz` and contains `pgdata` + `app-data` (ciphertext
and CA only, not the encryption key).

The recipe gates on `colima-agents` being running:

- VM down → recipe skips (so nightly `backup-all` doesn't fail).
- VM up → recipe stops containers, snapshots, restarts. `onecli down` refuses while connectome containers exist (see connectome's
  backup recipe for ordering).

`dotfiles stacks doctor` reports backup-age as `[OFF]` while `colima-agents` is stopped, and `[FAIL]` if the VM has been up
more than 36 hours without a fresh backup.

`dotfiles stacks onecli restore <tarball>` restores to empty volumes only (refuses to clobber). To reset:
`dotfiles stacks onecli down`, `docker --context colima-agents volume rm onecli_pgdata onecli_app-data`, then `restore`.

The v1 archive `~/.volume-backups/archive/onecli-v1-final.tgz` is outside GFS (permanent reference, kept separately).
